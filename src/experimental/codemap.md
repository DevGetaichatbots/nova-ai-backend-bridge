# backend/src/experimental/

## Responsibility
Versioned implementation archive for the schedule comparison agent pipeline and its HTML dashboard renderers. Contains a chain of analysis agents (`CompareV2Agent` → `CompareV3Agent` → `CompareV4Agent` → `CompareV5GraphAgent`), matching HTML formatters, and a pure-Python deterministic comparison engine for the Normaliseret UgeSchedule Format (NUSF). Each agent generation progressively extends the previous one: v2 returns basic scope-filtered activity diffs (added/removed/changed activities plus progress status and variance); v3 adds project-health metrics (executive summary with health colour, not-started-overdue detection, progress-vs-expected time-elapsed variance, stage mismatch, point-of-no-return classification, action recommendations); v4 introduces regex-based location extraction (floor/area/phase), trade-code detection, critical-path tracking, delay-driver analysis, and structured summary notes; v5 graph switches to a hybrid deterministic-first + LLM-enrichment architecture where exact counts are computed Python-side and the LLM only interprets and enriches. The formatters track the same lineage, evolving from a simple static HTML report (v2) to a fully interactive dashboard with a 4-dimensional client-side filter and SVG progress curve (v5 graph).

**Active production path**: Only `compare_v5_graph_agent` + `html_formatter_v5_graph` are wired to a live endpoint (`POST /v5-graph/compare` in `main.py`, which the V1.0 health dashboard wraps). The v3 and v4 agent modules are kept as base classes that v5-graph inherits from, and `html_formatter_v5` is imported internally by the v5-graph formatter. The standalone v2/v3/v4 endpoints (`/v2/compare`, `/v3/compare`, `/v4/compare`, `/v5/compare`) and the `/predictive/dashboard` endpoint have been removed; their dedicated formatter/agent modules are no longer reachable from any route and are retained only for regression testing and A/B benchmarking. `__init__.py` explicitly states this directory is NOT used in default production paths.

## Design
The agents employ a layered **Template Method** pattern via class inheritance. `CompareV2Agent` (`compare_v2_agent.py`) defines the base `analyze()` entry point: it calls `_resolve_scope_prefixes` to map a free-text scope filter to Danish trade-code prefixes via `SCOPE_FILTER_MAP` (a 19-key mapping of English keywords like `"electrical"`, `"plumbing"`, `"masonry"` to lists of Danish code prefixes such as `"EL -"`, `"VVS -"`, `"MU -"`), retrieves vector-store table chunks through `_retrieve_context` (with a 1.9 MB byte budget split evenly across stores, per-chunk truncation with warning logging), constructs a detailed system prompt instructing Azure OpenAI to output a specific JSON shape, parses the LLM response (stripping markdown fences), and applies `_postprocess` for Python-side scope enforcement, trivial-change removal (`old == new`), and deduplication.

`CompareV3Agent` (`compare_v3_agent.py`) subclasses and inherits `_retrieve_context` but replaces the post-processor with `_postprocess_v3`, which adds seven computed fields: `executive_summary` (project health via `_compute_project_health`, counts derived from data rather than LLM), `not_started_overdue` (0%-complete activities past their start date, validated Python-side with `_parse_date` across five date formats), `progress_vs_expected` (variance sorted most-negative-first), `stage_mismatch`, `point_of_no_return` (classification↔assessment mapping enforced via `_ponr_map` lookup), and `action_recommendations`. It also computes an optional Python-side activity count from vector store data (`true_selected_count`) and trade counts (EL/VVS/VENT/ARK/BYGH) for higher accuracy than LLM estimates.

`CompareV4Agent` (`compare_v4_agent.py`) inherits from `CompareV3Agent` and layers on **regex-based location extraction** with three layered pattern lists: `_FLOOR_PAT` (10 patterns for basement, ground floor, Nth floor, roof, etc.), `_AREA_PAT` (9 patterns for building/block/zone/wing references), and `_PHASE_PAT` (7 patterns for phase/etape/stage/section). Location is resolved via `_location_from_row` as a three-source fallback chain: `location_path`/`wbs_code` path parsing → row field regex → activity name regex. NUSF row parsing via `_extract_activity_rows` builds an `activity_metadata` index keyed by source_id or normalized name+location, enabling `_attach_locations` to enrich downstream sections. Trade-code detection (`_trade_code`) scans activity name, discipline, and task_group_name for prefix and keyword matches. `_postprocess_v4` wraps `_postprocess_v3` and appends `critical_path_activities`, `delay_drivers` (top 5), `filter_options` (sorted areas/floors/phases aggregated from all sections), and `summary_notes` with Python-computed overall progress deltas. A `require_nusf` flag validates that both schedules parse as NUSF before proceeding.

`CompareV5GraphAgent` (`compare_v5_graph_agent.py`) subclasses `CompareV4Agent` and introduces a **hybrid architecture**: when `require_nusf=True`, it fetches both table chunks, parses both via `parse_nusf_chunks`, and runs `nusf_compare_engine.compare_nusf_chunks` for deterministic row-level matching and all math (counts, progress, variance, PONR, critical path). It then builds a compact `_build_llm_packet` containing only computed facts (top behind/ahead, not-started, stage mismatches, activity index — not raw schedule text) and sends it to `_analyze_nusf_with_llm` which returns only enrichment fields: `project_health_override`, `delay_drivers`, `action_recommendations`, `critical_path_activities`, and `activity_enrichment` (trade/location inference). These are merged via `_merge_llm_analysis`, which also calls `_recompute_filters` and `_apply_activity_enrichment`. Falls back to `super().analyze()` (the v4 LLM-only path) when NUSF data is unavailable or `require_nusf=False`.

The formatters form a parallel hierarchy: `html_formatter_v2.format_compare_v2_as_html` renders v2 JSON with scope-list, change badges, progress-status table, and variance table; `html_formatter_v3.format_compare_v3_as_html` renders v3 JSON as a "Decision Dashboard" with executive-summary health badge, stat pills, change-summary pills, not-started table, progress vs expected table, stage-mismatch table, PONR cards, and action-recommendation cards; `html_formatter_v4.format_compare_v4_as_html` introduces a **client-side trade filter** (JS engine operating on `window.__v4Data` that re-renders six sections — KPI pills, status badge, top-5 issues, PONR list, WSID card, schedule tables, progress chart, and AI insights strip — when a trade pill is clicked); `html_formatter_v5.format_compare_v5_as_html` upgrades to a **4-dimensional filter** (trade, area, floor, phase) rendered as a sidebar with checkable filter options, a hero section with old/new progress panels and delta badge, and Danish/English locale support via `window.__v5Lang`; `html_formatter_v5_graph` is a decorator over `format_compare_v5_as_html` that injects an SVG progress-curve card (`_build_graph_card`), graph-drawing JS (`_GRAPH_JS_FUNCTION` with cubic bezier interpolation), and a data-quality warning banner via string replacement.

The `nusf_compare_engine` (`nusf_compare_engine.py`) is a **pure-Python deterministic engine** with no LLM dependency. It parses semicolon-delimited NUSF CSV chunks via `parse_nusf_chunks` (normalising headers via `_norm_header` which recognises Danish and English column names for source_id, name, planned_start, planned_finish, duration_hours, percent_complete, location_path, discipline, is_late, critical_flag, total_float; deduplicating by `_identity` key). `_resolve_activity_matches` implements a **greedy nearest-date pairing** algorithm: for each name+location group, it computes `_date_distance` (sum of start+finish day differences) for every old/new row pair, sorts by distance ascending, and greedily assigns matches (handles both unique-name groups with direct identity matching and multi-row groups where positional pairing would fail due to insertions/removals). `compare_nusf_chunks` orchestrates the full comparison: parses both schedules, matches activities, computes added/removed, generates change records with semantic value comparison (`_values_differ` handles date-parsed comparison and duration threshold), computes progress vs expected for every row (using `_expected_progress` for time-elapsed percentage and `_progress_status` for ahead/behind/on_schedule with actual-finish-date priority), classifies PONR (Red if ≤7 days remaining or variance ≤ -25%), detects critical path from explicit `critical_flag` or `total_float ≤ 0`, computes trade counts and summary statistics, and assembles a complete dashboard JSON structure matching the v5 agent contract. `build_progress_history_from_nusf_sources` assembles a multi-point time series of planned vs actual progress across several chronological extracts, falling back to actual-only trend when planned values are unavailable.

## Data & Control Flow
1. Caller invokes `agent.analyze(scope_filter, reference_date, table_names, session_id, old_filename, new_filename, top_k=50, require_nusf=False, language="en")`.
2. `scope_filter` (e.g. `"Electrical, BMS and Plumbing"`) is resolved to Danish trade-code prefixes via `_resolve_scope_prefixes` scanning `SCOPE_FILTER_MAP`. Empty match = no filter (all activities included).
3. V2/v3/v4 agents fetch table chunks from `vector_store_manager.fetch_all_from_stores(table_names, chunk_type="table")`. Each store is given an equal share of a 1.9 MB total byte budget; chunks exceeding the per-store budget are skipped with a warning. V4 additionally parses the new schedule's chunks via `_extract_activity_rows` to compute Python-side `true_selected_count` and `trade_counts`.
4. **V5 graph branch** (when `require_nusf=True` and both old/new chunks parse as NUSF): `nusf_compare_engine.compare_nusf_chunks(old_chunks, new_chunks, reference_date)` produces a complete deterministic result. `build_progress_history_from_nusf_sources` adds multi-extract progress history. `_analyze_nusf_with_llm` receives a compact `_build_llm_packet` (computed facts only, token budget ~4K) and returns enrichment. `_merge_llm_analysis` merges the two, then `_activity_index` is discarded.
5. **LLM-only branch** (v2–v4, or v5 fallback): The assembled context string is formatted into a detailed system+user prompt pair. Each generation's prompt instructs specific output sections with clearly numbered rules. The LLM (Azure OpenAI, `temperature=0`, `top_p=0.1`, `seed=42`, `max_tokens=16384`) returns a JSON response. The response is stripped of markdown (```json ... ``` fences) and parsed via `json.loads`.
6. Python-side post-processing validates/recomputes the JSON: scope filtering via `_activity_in_scope`, trivial-change removal, deduplication, PONR classification↔assessment consistency via `_ponr_map`, project-health computation via `_compute_project_health`, summary-note aggregation via `_compute_filter_options` and summary stats. Post-processors are chained: `_postprocess_v4` calls `_postprocess_v3` which calls `_postprocess`.
7. Error handling: every `analyze()` wraps the LLM call and post-processing in a `try/except` block that returns a zero-filled error object with `"error": str(e)` and `project_health: "Red"` in the `executive_summary`.
8. The result dict `{"json": data, "context_chunks": N}` is returned to the caller.
9. The matching `format_compare_v*_as_html` function renders the dict into a self-contained HTML string with embedded `<style>` and `<script>` blocks. V4+ formatters inject the full JSON as `window.__v*Data` for client-side JavaScript re-filtering without server round-trips.

## Integration Points
- **`backend/src/vector_store/vector_store_manager`** — `fetch_all_from_stores()` is the sole data source for every agent; called with `chunk_type="table"` to retrieve semicolon-delimited schedule contents.
- **`src.config.settings`** — Supplies `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_API_VERSION`, `AZURE_OPENAI_ENDPOINT`, and `AZURE_OPENAI_CHAT_DEPLOYMENT` to all agent classes.
- **`openai.AzureOpenAI`** — LLM inference client; all agents use identical inference parameters (`temperature=0`, `top_p=0.1`, `seed=42`, `max_tokens=16384`).
- **Production comparison pipeline** — Of the five agent generations, only `CompareV5GraphAgent` is wired into a live route (`POST /v5-graph/compare`, wrapped by `POST /version-1.0/health` in `src/main.py`). `CompareV3Agent` and `CompareV4Agent` are imported transitively as base classes for v5-graph; `html_formatter_v5` is imported transitively by `html_formatter_v5_graph`. The standalone `/v2/compare`, `/v3/compare`, `/v4/compare`, and `/v5/compare` routes were removed; their `compare_v2_agent` / `html_formatter_v2` / `html_formatter_v3` / `html_formatter_v4` modules are no longer reachable from any endpoint and are kept only for reference and regression testing. `__init__.py` states this directory is NOT used in default production paths.
- **`compare_v4_agent` depends on** `compare_v3_agent` (imports `SCOPE_FILTER_MAP`, `_resolve_scope_prefixes`, `_activity_in_scope`, `_parse_date`, `_compute_project_health`, `_postprocess_v3`, `CompareV3Agent`) and `nusf_compare_engine` (imports `parse_nusf_chunks`).
- **`compare_v5_graph_agent` depends on** `compare_v4_agent` (imports `CompareV4Agent`) and `nusf_compare_engine` (imports `parse_nusf_chunks`, `compare_nusf_chunks`, `build_progress_history_from_nusf_sources`).
- **`html_formatter_v5_graph` depends on** `html_formatter_v5` (imports `format_compare_v5_as_html` and injects additional CSS/JS/card/DOM markup via string replacement).
- **Dashboard front-end** — All v4+ formatters embed the full JSON as `window.__v4Data` / `window.__v5Data` and a locale pack as `window.__v5Lang` for client-side JavaScript filtering and Danish/English display.

## Public Surface
- `__init__.py` — Module marker; declares the directory as a reference/experimental archive.
- `compare_v2_agent.compare_v2_agent` — Singleton `CompareV2Agent`; `analyze()` returns scope-filtered activity changes and progress/variance data.
- `compare_v2_agent.SCOPE_FILTER_MAP` — Mapping of 19 English filter keywords to Danish activity-code prefixes (shared identically between v2 and v3).
- `compare_v2_agent._resolve_scope_prefixes(scope_filter)` — Resolves free-text filter string to deduplicated list of prefix strings.
- `compare_v2_agent._activity_in_scope(name, prefixes)` — Boolean check if an activity name starts with or contains any filter prefix.
- `compare_v2_agent._postprocess(data, scope_prefixes)` — Post-processes LLM output: filters scope_activities/changed_activities/progress_status/variance_analysis by prefix, removes trivial changes (old == new), deduplicates all lists.
- `compare_v3_agent.compare_v3_agent` — Singleton `CompareV3Agent`; `analyze()` returns v3 comparison with executive summary, project health, PONR, and action recommendations.
- `compare_v3_agent._postprocess_v3(data, scope_prefixes, reference_date)` — Post-processes v3 JSON with project-health computation, PONR classification↔assessment consistency enforcement, and computed executive summary.
- `compare_v3_agent._parse_date(val)` — Parses date strings across five European formats (DD-MM-YYYY, YYYY-MM-DD, DD/MM/YYYY, MM/DD/YYYY, DD.MM.YYYY).
- `compare_v3_agent._compute_project_health(data)` — Returns "Red"/"Yellow"/"Green" based on PONR red count, not_started_overdue, stage_mismatch, and behind-schedule counts.
- `compare_v4_agent.compare_v4_agent` — Singleton `CompareV4Agent`; `analyze()` returns v4 JSON with location metadata, critical path, delay drivers, filter options, and summary notes.
- `compare_v4_agent._postprocess_v4(data, scope_prefixes, reference_date, old_filename, new_filename, activity_metadata)` — Extends v3 post-processing with location attachment to progress/not_started/PONR sections, critical path validation, delay driver extraction (top 5), filter option computation, and summary notes with overall progress deltas.
- `compare_v4_agent._extract_location(name)` — Regex-based extraction of floor/area/phase from activity name using three layered pattern lists (10 floor patterns, 9 area patterns, 7 phase patterns).
- `compare_v4_agent._trade_code(name, row)` — Detects EL/VVS/VENT/ARK/BYGH trade from activity name, discipline, or task_group_name fields.
- `compare_v4_agent._extract_activity_rows(chunks, scope_prefixes)` — Parses semicolon-delimited chunk lines into structured activity rows with identity dedup and location metadata.
- `compare_v4_agent._attach_locations(items, activity_metadata)` — Attaches location dicts to progress/not_started/PONR/critical-path items from metadata index.
- `compare_v5_graph_agent.compare_v5_graph_agent` — Singleton `CompareV5GraphAgent`; hybrid deterministic+LLM analysis for the v5 graph dashboard variant.
- `compare_v5_graph_agent._merge_llm_analysis(base, llm_data)` — Merges LLM enrichment (health override, delay drivers, critical path, activity enrichment) into deterministic base result.
- `compare_v5_graph_agent._analyze_nusf_with_llm(deterministic_data, reference_date, old_filename, new_filename, language)` — Sends compact computed-facts packet (4K token budget) to LLM for interpretation/enrichment only.
- `compare_v5_graph_agent._build_llm_packet(data, reference_date, old_filename, new_filename)` — Assembles the LLM input packet from deterministic results with top-N truncation.
- `html_formatter_v2.format_compare_v2_as_html(data, language)` — Renders v2 JSON dict to a PM-dashboard-style HTML string with scope list, change cards, progress-status table, and variance table.
- `html_formatter_v3.format_compare_v3_as_html(data, language)` — Renders v3 JSON dict to a "Decision Dashboard" HTML string with health badge, stat pills, change-summary pills, not-started table, progress table, stage mismatch table, PONR cards, and action-recommendation cards.
- `html_formatter_v4.format_compare_v4_as_html(data, language)` — Renders v3 JSON to interactive HTML with inline JS trade filter engine (`v4SetFilter`) that re-renders all sections client-side.
- `html_formatter_v5.format_compare_v5_as_html(data, language)` — Renders v4/v5 JSON to interactive HTML with 4D sidebar filter (trade/area/floor/phase), hero progress panels, and Danish/English locale via `__v5Lang`.
- `html_formatter_v5_graph.format_compare_v5_graph_as_html(data, language)` — Renders v5 JSON to HTML with SVG progress curve card, cubic-bezier graph animation JS, and data-quality warning banner injected into the v5 formatter output.
- `nusf_compare_engine.parse_nusf_chunks(chunks)` — Parses raw vector-store chunks into normalised NUSF row dicts with header normalisation (Danish/English column names) and identity deduplication.
- `nusf_compare_engine.compare_nusf_chunks(old_chunks, new_chunks, reference_date)` — Pure-Python deterministic schedule comparison returning a full dashboard JSON structure with executive summary, changes, progress, PONR, critical path, delay drivers, and summary notes.
- `nusf_compare_engine.build_progress_history_from_nusf_sources(sources, reference_date)` — Builds a multi-point planned-vs-actual progress time series from multiple chronological NUSF extracts; falls back to actual-only trend if <2 planned points available.
- `nusf_compare_engine._resolve_activity_matches(old_rows, new_rows)` — Greedy nearest-date pairing of activities across schedule versions using `_date_distance` on start+finish dates.
- `nusf_compare_engine._progress_status(actual, expected, late_flag, planned_finish, actual_finish)` — Classifies an activity as ahead/behind/on_schedule with actual-finish-date priority over time-elapsed variance.
- `nusf_compare_engine._rescale_progress_if_fractional(rows)` — Converts 0–1 decimal progress scale to 0–100 percentage in-place, based on detecting max ≤ 1.0 across non-zero entries.
- `nusf_compare_engine._values_differ(change_type, old_val, new_val)` — Semantic value comparison for detecting changes: date-aware parsing for Start/Finish Date, threshold-based for Duration/Progress.
- `nusf_compare_engine._project_health(behind_count, red_ponr_count, critical_count, yellow_ponr_count)` — Deterministic health classification with configurable thresholds (≥3 yellow PONR or ≥5 behind triggers Yellow).
- `nusf_compare_engine._trade_code(row)` — Detects EL/VVS/VENT/ARK/BYGH trade from NUSF row fields (name, discipline, activity_type) with expanded keyword matching (includes SPRINKLER for VVS, GULV/BETON/ISOLERING/FACADE for BYGH).
- `nusf_compare_engine._location(row)` — Resolves location dict from NUSF row using `location_path` WBS-style parsing (`/`-separated parts), area inference from H8-style activity names (`_NK`/`_AP` suffixes), and direct area/floor/phase fields.
- `nusf_compare_engine._dashboard_meta(row)` — Assembles the metadata dict (id, source_id, location, resource, trade_code, duration) attached to every item in the deterministic output.
- `nusf_compare_engine._expected_progress(start, finish, ref)` — Computes time-elapsed expected progress percentage clamped to [0, 100].
- `nusf_compare_engine._parse_bool(value)` — Parses truthy values across formats (1, true, yes, y, ja).
- `nusf_compare_engine._norm_header(value)` — Normalises Danish and English column names to canonical keys (source_id, name, planned_start, planned_finish, duration_hours, percent_complete).
- `nusf_compare_engine._deduplicate_rows(rows)` — Removes duplicate activities by `_identity` key, keeping the last occurrence.
